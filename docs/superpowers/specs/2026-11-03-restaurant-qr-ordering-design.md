# 食刻扫码点单演示版设计

## 背景与目标

当前食刻是一个以汉堡 3D 试吃为核心的单路径互动体验：进入食物柜、选择汉堡、旋转模型并通过点击完成试吃。产品方向调整为餐厅扫码点单程序，3D 互动保留为菜品详情中的“虚拟试吃”，服务于顾客看菜和选择，而不是作为首页的唯一目的。

本阶段交付一个纯前端、可演示的点单闭环：顾客通过带桌号的 URL 进入菜单，浏览菜品，查看详情和可用的 3D 试吃，选择规格与数量，加入购物车，确认桌号和订单，提交后看到本地模拟订单号与状态。它不包含真实支付、后厨同步、库存、账号或服务端收单。

## 产品边界

### 本阶段包含

- 从 `?table=A01` 读取并规范化桌号；没有桌号时显示扫码桌码提示，并允许使用演示桌号进入预览。
- 餐厅菜单首页、分类筛选、菜品卡片、价格、简介和购物车入口。
- 菜品详情抽屉或页面，支持图片封面；有 3D 素材的菜品显示“虚拟试吃”入口。
- 汉堡保留现有四阶段 3D 试吃、旋转、点击进食、音效、进度和完成反馈；试吃完成后可回到菜品详情并加入点单。
- 规格选择、数量调整、备注、购物车明细、金额合计和删除。
- 确认订单页展示桌号、菜品明细、合计和提交按钮。
- 提交后生成本地演示订单号、记录创建时间，显示“已收到订单”的结果页。
- 购物车和最近一次演示订单使用 `localStorage` 恢复；同一桌号的菜单 URL 可以刷新继续演示。
- 桌号、购物车金额、订单状态和菜单数据使用独立模块，避免让 `App.tsx` 承担所有业务逻辑。

### 本阶段不包含

- 支付、优惠券、会员、发票、退款。
- 服务端 API、真实订单推送、店员端、厨房屏、库存和菜品后台。
- 多人同桌合并、并发冲突、账号登录。
- 强制所有菜品都提供 GLB；没有模型的菜品使用图片详情即可。

## 核心用户流程

```text
扫码进入 /?table=A01
        |
        v
菜单首页 --分类筛选--> 菜品详情 --规格/数量--> 加入购物车
   |                       |
   |                       +--> 虚拟试吃 --> 试吃完成 --> 返回详情
   v
购物车 --> 确认订单 --> 提交演示订单 --> 订单结果
```

没有桌号时，菜单仍可浏览和查看菜品；进入确认订单时必须补充一个演示桌号或返回扫码提示。这样分享无参数的首页不会被空白错误阻断，但订单不会产生无归属桌号。

## 数据模型

保留现有 `FoodDefinition` 作为 3D 素材运行时契约，在其上建立菜单层，而不是把价格和购物车字段塞入模型阶段定义。

```ts
interface MenuItem {
  id: string;
  name: string;
  category: '推荐' | '主食' | '小食' | '饮品';
  description: string;
  price: number;
  cover: string;
  foodId?: string;        // 有值时关联 FoodDefinition，启用 3D 试吃
  options?: MenuOption[];
  available: boolean;
}

interface MenuOption {
  id: string;
  name: string;
  choices: { id: string; label: string; priceDelta: number }[];
}

interface CartLine {
  lineId: string;         // item + normalized options，保证相同选择可合并
  itemId: string;
  name: string;
  unitPrice: number;
  quantity: number;
  options: { groupId: string; choiceId: string; label: string; priceDelta: number }[];
  note: string;
}

interface DemoOrder {
  id: string;
  table: string;
  lines: CartLine[];
  total: number;
  createdAt: string;
  status: 'received';
}
```

价格使用整数分进行计算，界面显示为元，避免浮点累加误差。菜品、规格选择和购物车操作使用纯函数；UI 只负责收集动作和呈现状态。

## 模块与状态边界

- `src/data/menu.ts`：菜单分类、菜品价格、封面、规格和可选 `foodId`。当前汉堡作为第一个可试吃菜品，其他演示菜品可以先使用现有首页插画或稳定的占位封面。
- `src/core/table.ts`：解析、规范化和校验 URL 桌号；只允许短字母数字和连字符，统一大写。
- `src/core/cart.ts`：添加、合并、修改数量、删除、计算小计和总价；无浏览器依赖，便于单元测试。
- `src/core/orders.ts`：生成订单号、保存和读取本地演示订单；不模拟远端成功以外的网络状态。
- `src/ui/MenuHome.tsx`、`MenuItemDetail.tsx`、`CartSheet.tsx`、`OrderReview.tsx`、`OrderResult.tsx`：按用户流程拆分页面层。
- `src/App.tsx`：只持有当前页面、桌号、购物车和详情选择等顶层状态，并负责路由式切换；3D 试吃复用现有 `PlayScreen`。

状态流转使用显式页面状态：`menu`、`detail`、`tasting`、`cart`、`review`、`result`。返回操作保留当前购物车；提交成功后清空购物车并保留订单结果，刷新时优先恢复最近订单结果。

## 视觉与交互方向

保留当前餐厅招牌、美漫线条、奶油纸张和红棕强调色，但信息层级改为餐厅菜单：顶部显示餐厅名、桌号和购物车金额；菜单先看分类与菜品，再进入详情。价格、规格和加入点单按钮应始终清楚可见。3D 试吃作为详情中的高价值动作，使用明确的“虚拟试吃”标签，完成后显示“加入点单”。

移动端优先适配扫码场景：底部固定购物车摘要，触控目标至少 44px，详情和购物车可关闭并回到原位置。桌号缺失时使用轻量提示条，不覆盖菜单浏览。

## 错误与恢复

- 非法桌号被视为缺失桌号，不进入订单确认；用户可从提示中查看需要的扫码入口。
- 菜品不可售时保留卡片和详情，但禁用加入点单并说明“暂时售罄”。
- 本地存储损坏或版本不匹配时丢弃损坏数据，恢复为空购物车并继续浏览。
- 3D 模型加载失败沿用现有重试和降级行为；图片加载失败显示菜品首字 fallback。
- 订单提交只写入本地存储；写入失败时显示可重试提示，不清空购物车。

## 测试与验收

### 单元测试

- 桌号缺失、大小写、非法字符和长度边界。
- 购物车添加相同或不同规格时的合并规则、数量上下限、删除和金额计算。
- 订单号格式、总价快照、序列化恢复和损坏数据处理。
- 菜单中有无 `foodId` 时试吃入口的显示规则。

### 浏览器测试

- 带桌号进入菜单，按分类筛选，打开汉堡详情并进入试吃，再回到详情。
- 选择规格和数量，加入购物车，修改数量，确认总价，提交后看到订单号和桌号。
- 刷新后购物车或最近订单结果恢复。
- 无桌号浏览菜单，但确认订单时得到明确的桌号提示。
- 售罄菜品不可加入，菜单和详情仍可访问。
- 保留现有 3D 试吃、加载失败恢复、旋转和移动端回归测试。

验收标准是：首次打开带桌号 URL 的顾客可以在不依赖网络 API 的情况下完成一条完整演示订单；汉堡 3D 试吃仍能从详情进入并返回；刷新不会意外丢失购物车；金额计算和订单桌号与提交前一致。

## 后续演进

演示版稳定后，再将 `orders.ts` 的本地存储适配为服务端接口，增加订单状态轮询或推送；支付和厨房流程作为独立阶段加入，不提前污染本阶段的数据边界。
